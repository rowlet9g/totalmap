# Totalmap 개발 인수인계 및 작업 지침

마지막 갱신: 2026-09-22  
작업 폴더: `C:\Users\yount\totalmap`

이 문서는 Totalmap 프로젝트를 이어서 개발할 사람 또는 에이전트를 위한 단일 인수인계 문서다. 현재 상태, 사용자 요구, 검증된 사실, 아직 검증되지 않은 가정, 다음 작업 순서를 함께 기록한다.

## 1. 가장 먼저 알아야 할 현재 상태

**실제 지도 계정의 자동 동기화는 아직 작동하지 않는다.**

현재 구현된 것은 다음 범위다.

- 동기화 정책과 상태 모델
- 최초 합집합 및 이후 추가·삭제·분류 이동 계획 생성
- 충돌, 불완전 조회, 계정 변경, 목록 변경 감지
- 중단·응답 유실을 고려한 작업 실행 프로토콜
- Whale용 읽기 진단 확장 프로그램
- 로컬 관리 화면과 진단 수신 서버

실제 네이버지도·카카오맵·Google 지도용 완전한 읽기 어댑터와 쓰기 어댑터는 아직 없다. 실제 계정의 장소 추가, 삭제, 이동, 메모 변경도 한 번도 실행하지 않았다.

### 매우 중요한 판정 규칙

- 진단에서 `0개`가 나오더라도 저장 목록이 비었다는 뜻이 아니다.
- `complete: false`인 결과는 동기화 입력이나 삭제 판정에 절대 사용하지 않는다.
- 세 서비스·네 분류의 완전한 조회와 안정적인 장소 연결을 확보하기 전에는 쓰기 기능을 활성화하지 않는다.
- 테스트 통과는 순수 동기화 로직의 검증이며 실제 지도 사이트 자동화 성공의 증거가 아니다.

## 2. 사용자가 확정한 목표와 정책

Whale Browser에 로그인된 네이버지도, 카카오맵, Google 지도의 개인 저장 장소를 동기화한다.

### 목록 대응

| 통합 분류 | 네이버지도 | 카카오맵 | Google 지도 | 참고 수량 |
|---|---|---|---|---:|
| `landmark` | 내 장소 | 기본 그룹 | landmark | 115 / 103 / 79 |
| `cuisine` | cuisine | cuisine | cuisine | 722 / 124 / 158 |
| `cafeteria` | cafeteria | cafeteria | cafeteria | 101 / 101 / 74 |
| `bar` | bar | bar | bar | 63 / 60 / 11 |
| 합계 | 1,001 | 388 | 322 | 총 1,711개 목록 소속 항목 |

위 수량은 사용자 첨부 화면에서 읽은 참고값이다. 실제 고유 장소 수가 아니며, 완전한 현재 조회의 증거로 사용하면 안 된다.

### 동기화 규칙

- 국내 장소만 세 서비스 사이에 동기화한다.
- 해외 장소는 Google 지도에 그대로 두고 네이버·카카오로 전파하지 않는다.
- 국가를 확정하지 못한 장소는 보류한다.
- Google의 `Saved places`와 `여행 계획`은 완전히 무시한다.
- 각 서비스의 기존 목록 이름은 유지하고 내부적으로 대응 목록 ID를 연결한다.
- Google의 기존 공유 목록에 장소를 추가해도 된다.
- 메모는 서비스 사이에 복사하지 않는다.
- 기존 메모는 작업 난이도가 낮고 안전하게 메모만 제거할 수 있을 때 삭제를 검토한다. 복잡하거나 불안정하면 메모가 있는 장소만 사용자에게 보고한다.
- 최초 연결은 네 분류별 국내 장소의 합집합을 만든다.
- 최초 기준 상태가 완성된 뒤에는 사용자의 추가, 목록에서 제거, 분류 이동을 다른 두 지도에 전파한다.
- 한 장소가 여러 분류에 동시에 속할 수 있으며 각 소속을 독립적으로 보존한다.

### 삭제의 의미

삭제는 지도에서 장소 자체를 없애는 작업이 아니다. 사용자가 특정 저장 목록에서 장소를 제거한 변경을 다른 지도에도 반영하는 뜻이다.

## 3. 현재 구현 구조

### 핵심 로직

- `extension/core/config.js`
  - 서비스, 네 분류, 목록명 대응, 참고 수량, 확정 정책

  - 작업 전후 재조회

  - 분류 이동 시 새 분류 추가를 먼저 검증한 뒤 기존 분류 제거
  - 작업 중 사용자 변경 감지
- `extension/core/links.js`
  - 지도별 장소 URL과 ID 정규화

### Whale 확장

- `extension/manifest.json`
  - Manifest V3
  - 기본 권한: `activeTab`, `scripting`, `storage`

- `extension/capture.js`
  - 현재 페이지와 접근 가능한 프레임의 링크 및 제한된 화면 구조 진단
  - 스크립트, 입력 필드, 쿠키, storage, 네트워크 응답은 수집하지 않음
- `extension/popup.*`
  - 분류 선택, 네이버 저장 패널 선택 권한 요청, 현재 화면 읽기
- `extension/dashboard.*`
  - 정책·참고 수량·진단 기록·계획 미리보기
- `extension/storage.js`
  - 확장에서는 `chrome.storage.local`, 일반 미리보기에서는 `localStorage`

### 최초 읽기 실패의 원인

세 서비스에서 처음 `0개`가 표시되었다. 이는 목록이 비었기 때문이 아니라, 최초 수집기가 눈에 보이는 `<a href>` 형태의 장소 링크만 검사했기 때문이다.

네이버의 실제 진단 파일:

`data/diagnostics/1790042911478-naver-0f23d115-34ef-46bd-82c0-748ab9941c3d.json`

이 파일에서 확인한 사실은 다음과 같다.

- 최상위 페이지는 `map.naver.com`이다.
- 바깥 페이지에 iframe이 6개 존재한다.
- 읽힌 결과는 바깥 지도 프레임 1개뿐이다.
- 저장 목록이 들어 있는 패널 내부 DOM은 읽히지 않았다.
- 현재 열린 네이버 폴더 URL에는 폴더 ID가 포함되어 있다.
  - `/p/favorite/myPlace/folder/7ebdcbab96084e56b8d4a01b9ab34af3`
- 바깥 DOM에는 저장 메뉴와 지도 마커 군집만 보이며 목록의 722개 장소 행은 없다.

따라서 네이버 저장 목록은 교차 출처 내부 프레임에 있고, 기존 `activeTab` 권한만으로 내부 내용을 수집하지 못한 것으로 판단했다.

### 마지막으로 적용한 변경

- `manifest.json`에 네이버 저장 패널용 선택 host 권한 추가
- 팝업에 `네이버 저장 패널 연결 (최초 1회)` 버튼 추가
- 수집 결과에 `frameId` 기록
- 허용 프레임 주소에 `pages.map.naver.com` 추가
- `0개`를 빈 목록 성공으로 표시하지 않고 읽기 미지원으로 설명
- 자동 진단 전달 실패 시 JSON 다운로드 시도

이후 받은 재진단 `data/diagnostics/1790057384078-naver-6ce0d3c3-8734-471e-a298-5a50882cc4d3.json`에서는 바깥 지도와 `pages.map.naver.com` 내부 패널 두 프레임이 읽혔다. 내부에는 `cuisine`, 표시 개수 718개, 장소 카드 구조가 있다. 이는 전체 장소 수집 성공을 뜻하지 않으며 안정적인 장소 ID는 아직 미확인이다.

외부 도구가 추가했던 무차별 `dataset` 값 수집을 제거하고 다음 제한을 적용했다.

- `pages.map.naver.com`의 실제 진단에서 확인된 `ul._place_card_list_…` 아래 `li._place_info_card_…[role=button]` 형태에만 속성 이름 진단 적용.
- `data-*` 이름을 최대 20개 기록하며 값은 열거하지 않음.
- 값 허용 목록은 현재 비어 있음. `data-id`나 `data-place-id`라는 이름만으로 장소 ID라고 가정하지 않음.
- 실제 의미를 확인한 숫자형 장소 ID 속성만 추후 허용 목록에 추가. 다른 형식의 ID를 발견하면 해당 형식의 검증 규칙부터 별도로 검토.
- 수정된 확장의 실사용 재진단은 아직 미실행.

## 5. 바로 다음에 해야 할 일

### 1단계: 네이버 내부 프레임 읽기 재검증

현재 내부 프레임 접근은 위 재진단으로 확인됐다. 다음은 확장을 새로고침하여 장소 카드의 `dataAttributeNames`를 확인하는 단계다. 아래 권한 연결 절차는 새 설치 또는 권한 누락 시에만 반복한다. 이미 부여한 권한을 매번 다시 요청하지 않는다.

1. 로컬 진단 수신기를 실행한다.

   ```powershell
   node scripts/diagnostics.mjs
   ```

2. 사용자에게 다음 동작을 요청한다.
   - `whale://extensions`에서 Totalmap 새로고침
   - 네이버 `cuisine` 목록 열기
   - Totalmap 팝업에서 `네이버 저장 패널 연결 (최초 1회)` 클릭
   - 브라우저 권한 허용
   - `현재 지도 읽기` 클릭

3. `data/diagnostics`에 새 JSON이 도착했는지 확인한다.
4. 새 결과의 `frames`가 1개보다 많은지, `pages.map.naver.com` 내부 구조와 목록 행이 포함됐는지 확인한다.
5. 권한을 허용했는데도 프레임이 빠지면 다음을 순서대로 점검한다.
   - 실제 iframe origin이 `pages.map.naver.com`인지 진단의 `frameSources`로 확인
   - Manifest V3의 `allFrames: true` 주입이 Whale에서 선택 권한 프레임에 적용되는지 확인
   - 프레임이 sandboxed 또는 별도 확장 제한을 받는지 확인
   - 필요한 정확한 host 권한만 추가

내부 프레임을 읽기 전에는 네이버 장소 행 selector를 추측하여 구현하지 않는다. 현재 확인된 카드 구조가 변경되면 추가 진단으로 확인하고, 임의 속성 값 수집으로 되돌아가지 않는다.

### 2단계: 네이버 완전 목록 수집기

내부 구조가 확보되면 다음을 구현한다.

- 목록명과 목록 ID 확인
- 장소 행에서 안정적인 장소 ID, 이름, 주소 또는 연결 근거 추출
- 가상 스크롤 목록 끝까지 순차 수집
- 표시된 전체 개수와 고유 장소 ID 수 비교
- 스크롤 중 목록 변경 여부 확인
- 중복 행 제거
- 로그인 만료와 로딩 오류 판별
- 모든 조건을 만족할 때만 `complete: true`

페이지에서 관찰된 내부 요청이나 비공개 엔드포인트를 사용하려면 우선 실제 동작·약관·안정성을 별도로 검토한다. 현재 프로젝트는 비공개 API나 쿠키 추출을 사용하지 않는다. 공개 웹에서 발견한 과거 엔드포인트 예시는 구현 근거로 채택하지 않았다.

### 3단계: 카카오·Google 진단

네이버 수집기를 바로 일반화하지 않는다. 같은 `cuisine` 표본으로 카카오와 Google에서 새 진단을 각각 받아 다음을 분리하여 확인한다.

- 장소 목록이 최상위 DOM인지 iframe인지
- 장소가 링크인지 버튼/가상 행인지
- 목록 ID와 장소 ID를 어디서 안정적으로 얻을 수 있는지
- 전체 개수와 목록 끝을 어떻게 증명할 수 있는지

서비스별 어댑터를 별도로 만들고 공통 스냅샷 계약에 맞춘다.

### 4단계: 장소 매칭과 국가 판별

세 서비스의 완전 조회가 가능해진 뒤 구현한다.

- 서비스별 안정 ID를 내부 canonical place에 연결
- 상호명만 사용하지 않고 주소, 지점명, 좌표, 전화번호 등 가능한 근거 조합
- 국내/해외/미확인 판정 근거 기록
- 애매한 후보는 자동 연결하지 않고 확인 대기
- 한 번 확정된 연결은 baseline의 `refs`로 고정

### 5단계: 읽기 전용 전체 비교

실제 쓰기 전에 관리 화면에서 다음을 검토할 수 있어야 한다.

- 분류별 세 서비스의 합집합
- 각 서비스에 빠진 장소
- 해외 및 국가 미확인 제외 목록
- 매칭 충돌과 미확인 장소
- 메모 존재 여부를 안전하게 알 수 있다면 별도 표시

사용자가 결과를 검토한 뒤에만 쓰기 어댑터 개발로 넘어간다.

### 6단계: 소량 쓰기 검증

실제 쓰기 어댑터를 구현한 뒤에도 전체 1,711개를 즉시 처리하지 않는다.

- 서비스별 표본 장소로 추가 검증
- 추가 후 재조회로 실제 저장 확인
- 분류 이동은 대상 분류 추가 검증 후 원래 분류에서 제거
- 응답 유실 시 버튼을 다시 토글하지 않고 현재 상태부터 확인
- 작업 기록을 디스크에 원자적으로 저장
- 실패·세션 만료·사용자 개입 시 해당 장소를 중단

표본 검증이 끝난 후 최초 합집합, 이후 주기 동기화 순으로 확장한다.

## 6. 절대 지켜야 할 안전 조건

- 불완전 조회를 삭제로 해석하지 않는다.
- 계정이 달라졌거나 목록 ID가 바뀌면 작업을 중단한다.
- 장소 연결이 사라지거나 바뀌면 자동으로 다시 연결하지 않는다.
- 국가 정보가 `UNKNOWN`이면 전파하지 않는다.
- 여러 서비스에서 동시에 다른 변경이 발생하면 순서를 추측하지 않는다.
- 쓰기 응답만으로 성공 처리하지 않고 실제 목록 소속을 재조회한다.
- 이동 중 대상 분류 추가가 실패하면 기존 분류에서 제거하지 않는다.
- 사용자의 수동 변경과 자동화의 부분 적용을 job 기록으로 구분한다.
- 로그인 쿠키, 토큰, 비밀번호를 출력·저장·전송하지 않는다.
- 진단 파일에는 화면 텍스트가 포함될 수 있으므로 저장소에 커밋하지 않는다. `data/`는 `.gitignore` 대상이다.
- Google의 `Saved places`, `여행 계획`과 해외 장소에는 쓰기 작업을 만들지 않는다.

## 8. 완료 기준

프로젝트 완료는 다음 조건을 모두 만족할 때다.

1. 세 서비스의 네 대상 목록을 완전하게 읽는다.
2. 표시 개수와 고유 장소 항목이 일치하고 조회 완전성을 증명한다.
3. 국내 장소의 서비스 간 연결과 국가 판정이 검토 가능하다.
4. 최초 합집합을 중복 없이 반영한다.
5. 이후 추가·삭제·분류 이동을 양방향으로 전파한다.
6. 해외 장소와 Google 제외 목록은 건드리지 않는다.
7. 실패·응답 유실·로그인 만료·동시 변경 후에도 잘못 삭제하거나 부활시키지 않는다.
8. 모든 쓰기 작업은 기록되고 재조회로 검증된다.
9. 메모는 복사하지 않으며, 기존 메모 처리 결과를 사용자에게 명확히 보고한다.
10. 사용자가 관리 화면에서 변경 예정과 결과를 확인할 수 있다.
