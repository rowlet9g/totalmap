# Totalmap 기능 점검과 구현 순서

점검일: 2026-09-23. 현재 코드, 테스트, 사용자가 제공한 실제 네이버 진단을 기준으로 작성했다.

2026-10-06 갱신: 아래 표는 최초 점검 당시 상태다. 이후 정상화와 상세 URL 읽기를 구현했고, 선택한 네이버 상세 홈의 이름·주소 자동 읽기는 스팀하우스 인덕원점 표본으로 사용자 실사용 확인을 받았다. 최신 구현·검증 범위는 [STEP1_NAVER_FIELDS.md](STEP1_NAVER_FIELDS.md)를 참조한다. 전체 목록 조회와 실제 동기화는 여전히 미구현이다.

## 결론

현재 제품은 **읽기 진단 도구 + 동기화 계획기/실행 프로토콜의 원형**이다. 실제 세 지도 저장 목록 동기화는 동작하지 않는다. 네이버 전체 목록 수집부터 구현해야 하며, 지도 저장 버튼을 자동으로 누르는 작업은 그 이후다.

## 실제 네이버 진단이 말해 주는 것

근거: 사용자 제공 `totalmap-diagnostics-1790142374950.json`, 캡처 시각 `2026-09-23T05:46:12.895Z`.

- 내부 `pages.map.naver.com` 프레임 접근은 성공했다. 권한 연결을 반복할 단계는 아니다.
- 표시 개수는 718개지만 구조에 포함된 카드는 20개다. 현재 로딩된 범위의 증거일 뿐이다.
- 카드 20개 모두 `dataAttributeNames`가 빈 배열이다. 같은 속성 진단을 반복해도 현재 증거로는 장소 ID를 얻지 못한다.
- 장소 링크 후보는 0개, `complete`는 false다. 저장 목록이 비었다는 의미가 아니다.
- 카드 선택 뒤 상세 화면 URL/공유 링크에서 장소 ID가 나오는지는 아직 확인하지 않았다. 다음 실기 조사 대상이며 확정된 해결책은 아니다.

## 재검토 중 발견한 연결 단절

1. **진단과 동기화 입력은 다른 형식이다.** 내보내기는 `captures`, 계획기 가져오기는 `snapshots`와 `places`를 요구한다. 다운로드한 JSON을 계획기에 넣어도 동기화되지 않는다.
2. **미리보기와 확장의 저장소는 별개다.** `127.0.0.1:47831`은 웹 localStorage, 확장 관리 화면은 chrome.storage.local을 쓴다. 진단 수신기는 디스크에 쓰기만 하며 미리보기로 데이터를 읽어 보내는 기능이 없다.
3. **수량은 참고 상수다.** 관리 화면의 네이버 1,001개 등은 최초 사용자 스크린샷 기준이며 실제 수집 진척률이 아니다. 722와 최신 진단 718의 차이를 자동 삭제로 해석할 근거도 없다.
4. **계획기와 실행기가 제품 흐름에 연결되지 않았다.** dashboard는 planSync만 사용하며 createJob/resumeJob/checkpoint를 호출하지 않는다.
5. **영구 기록과 동시 실행 제어는 계약뿐이다.** 일반 설정/진단 저장 함수는 있으나 작업별 저장, 실행 잠금, 충돌 복구가 연결되지 않았다. load→수정→save 방식은 동시 저장 시 덮어쓰기 가능성도 검토해야 한다.
6. **입력 검증 UI를 보강해야 한다.** 가져오기는 planSync가 반환한 issues를 검사하지 않고 입력을 보관한다. 보관 성공과 유효한 실행 입력을 분리해서 표시해야 한다. 임의 JSON에 대한 스키마 검증도 부족하다.
7. **제외 정책의 실서비스 적용을 검증해야 한다.** ignoredGoogleLists는 설정에 있지만 실제 목록 연결기가 없다. 잘못 분류된 제외 목록까지 보호되는 것으로 간주하면 안 된다.
8. **메모 미복사와 진단 비수집은 다르다.** 수집기는 일반 요소의 직접 텍스트를 기록한다. 카드 안에 메모가 일반 텍스트로 표시된다면 기록될 여지가 있으므로 메모 미수집을 보장한다고 표현하지 않는다. 전용 수집기는 필요한 필드만 읽도록 설계한다.
9. **장시간 작업 수명과 기간 검증이 필요하다.** 현재 popup 클릭 핸들러로 수백 개를 순회하는 구조는 없다. 확장 팝업 종료/탭 이동/로그아웃/브라우저 종료에 대한 중단·복구 설계를 먼저 한다. 전체 수집 시간이 계획기의 30분 유효기간과 양립하는지도 실제 측정한다.

## 권장 구현 순서와 통과 기준

### 1. 네이버 장소 한 개를 정확하게 읽기 — 가장 먼저

- 실제 카드 한 개를 선택해 상세 화면이 어디에서 열리는지 확인한다.
- 목록 ID, 장소 ID, 상호명, 주소의 출처를 각각 확인한다. 이름/배열 순서를 장소 ID로 사용하지 않는다.
- 목록으로 돌아와 같은 장소를 다시 읽어도 ID와 목록 소속이 유지되는지 확인한다.
- 다른 카드와 동명 지점을 포함한 소수 표본으로 검증한다. ID가 제공되지 않는 장소는 미확인으로 남긴다.
- **통과 기준:** 동일 장소는 재조회에서도 같은 ID, 서로 다른 장소는 다른 ID. 단순 이름 수집으로 완료 처리하지 않는다.

### 2. 네이버 목록 하나를 끝까지 읽기

- 스크롤/추가 로딩, 중복 제거, 로딩 실패, 끝 판정, 수집 중 변경 감지와 계정 확인을 구현한다.
- 진행률을 `표시 개수 / 고유 ID 수집 수 / 미확인 수 / 완료 여부`로 분리한다.
- 긴 작업은 팝업 UI에서 분리하고 중간 상태와 중단 이유를 저장한다. 구체적인 실행 위치는 1단계에서 확인한 페이지 구조에 맞춰 정한다.
- **통과 기준:** 그 시점의 목록 전체 개수와 고유 항목이 일치하고 끝/계정/목록/안정성을 확인한다. 중단하거나 일부 항목에 실패하면 complete=false.

### 3. 네이버 네 분류 및 다른 두 서비스 읽기

- 네이버 네 분류의 실제 목록 ID를 연결하고 한 장소의 다중 소속을 유지한다.
- 카카오와 Google은 각각 소수 표본→목록 하나→대상 네 목록 순서로 전용 수집기를 만든다.
- Google 제외 목록은 실제 목록 ID로 범위에서 제외한다. 대상 목록에 포함된 해외 장소는 전체 조회 검증에 포함하되 타 서비스로 전파하지 않는다.
- **통과 기준:** 세 서비스 × 네 분류의 검증된 스냅샷을 생성하고, 계정 교체/로그아웃/목록 누락을 오류로 구분한다.

### 4. 국가 판별·장소 매칭·읽기 전용 비교 화면

- 주소/국가/지점/좌표 등 확인 가능한 근거로 연결하며 자동 판정 불가 항목은 검토 대기로 남긴다.
- 어느 지도에도 저장되지 않은 대상 서비스 장소는 검색/상세 조회로 찾는 기능도 필요하다.
- 목록 이름·ID 연결, 해외/미확인/충돌, 서비스별 누락을 관리 화면에 표시한다.
- 실제 확장 관리 화면을 주 화면으로 삼고 미리보기는 데모임을 명확히 한다. 진단 자료와 검증 스냅샷 가져오기를 구분한다.
- **통과 기준:** 대표 표본의 연결 근거를 검토할 수 있고, 해결되지 않은 항목은 실행 작업으로 넘어가지 않는다.

### 5. 영구 작업 기록을 연결하고 소량 쓰기 검증

- 작업별 영구 저장, 단일 실행 잠금, 중단/재개, 세션 만료 처리와 실패 표시를 구현한다.
- 서비스별 추가 어댑터를 먼저 만들고 소수 장소로 쓰기 후 재조회한다. 기존 공유 목록 권한도 실제 확인한다.
- **통과 기준:** 응답 유실/재시작 후 중복 토글 없이 복구하고, 저장 실패는 성공으로 표시하지 않는다.

### 6. 최초 합집합 반영 → 기준 상태 → 삭제/이동

- 최초에는 필요한 추가만 수행한다. 완료 후 세 서비스를 다시 읽어 일치할 때 baseline을 저장한다.
- 그 뒤 한 서비스의 수동 추가/제거/이동을 검증하고, 동시 변경은 충돌로 표시한다.
- **통과 기준:** 이동 대상 저장 실패 시 기존 소속을 제거하지 않으며, 삭제된 소속이 재시작 후 부활하지 않는다.

### 7. 주기 실행과 메모 보고

- 주기 스캔, 요청 간격, 재시도 제한, 탭/브라우저 종료 후 재개를 연결한다.
- 메모는 우선 존재 여부 보고까지만 구현한다. 본문을 복사하지 않으며 삭제는 별도 기능으로 비용과 정확성을 평가한다.
- **통과 기준:** 반복 실행 시 불필요한 쓰기가 없고 사용자가 마지막 성공/중단 원인을 확인할 수 있다.
