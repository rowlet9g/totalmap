# 스냅샷과 장소 연결 계약

`planSync({ snapshots, places, baseline? })`는 변경 계획만 반환합니다. 외부 저장을 변경하지 않습니다. `checkpoint()`는 새 조회에서 세 서비스가 모두 같은 상태이고 해결할 문제가 없을 때만 기준 상태를 생성합니다.

## 입력

```json
{
  "snapshots": [{
    "provider": "naver",
    "accountId": "local-account-fingerprint",
    "authenticated": true,
    "complete": true,
    "capturedAt": "2026-09-22T04:00:00Z",
    "lists": [{
      "id": "actual-list-id",
      "name": "cuisine",
      "category": "cuisine",
      "complete": true,
      "expectedCount": 1,
      "items": [{ "placeId": "123" }]
    }]
  }],
  "places": [{
    "id": "canonical-uuid",
    "country": "KR",
    "refs": {
      "naver": { "id": "123" },
      "kakao": { "id": "456" },
      "google": { "id": "google-stable-id" }
    }
  }]
}
```

위 예시는 구조 설명용이며 세 서비스·네 분류가 모두 포함되지 않아 계획 실행 요건을 충족하지 않습니다. 진단 JSON과도 별개의 형식입니다.

- 세 서비스별 스냅샷 정확히 하나, 각 서비스의 네 분류 정확히 하나씩 필요합니다.
- accountId는 로그인 상태를 실제 확인한 로컬 계정 식별자여야 하며 쿠키/토큰을 사용하면 안 됩니다.
- complete는 단순히 개수가 같다는 뜻이 아닙니다. 어댑터가 로그인·선택 목록·페이지 끝·중복·수집 중 변경 여부를 확인한 뒤에만 true를 기록해야 합니다.
- expectedCount는 해당 시점 서비스 화면/조회 결과의 전체 개수입니다. 첨부 화면 참고 수치를 넣으면 안 됩니다. 해외 항목도 해당 목록 전체 개수에 포함됩니다.
- 장소 ID와 목록 ID는 서비스에서 확인한 안정적인 값이어야 합니다. 제목이나 화면 배열 인덱스는 ID로 쓰면 안 됩니다.
- 명칭만 같다고 장소를 연결하면 안 됩니다. 국가·주소·지점 등 충분한 근거로 확인한 뒤 refs를 작성합니다. 장소 이동/폐업/중복 ID 변경은 수동 확인 대상입니다.
- Google CID와 Places API place_id는 다른 식별자 체계입니다. 두 값을 임의로 동일시하지 않습니다. 현재 링크 진단은 이를 구분하여 기록합니다.
- 국가 UNKNOWN은 보류합니다. 국가 코드는 추정 문자열이 아닌 검증된 값이어야 합니다.
- 메모 문자열은 스냅샷에 필요하지 않습니다. 추후 notePresent만 별도로 기록할 수 있습니다.
- 최신 조회는 30분 이내이고, 이전 기준 상태보다 과거이면 안 됩니다. 실제 전체 수집 소요시간 검증 후 정책을 조정할 수 있습니다.

## 기준 상태와 충돌

처음은 분류 소속의 합집합입니다. 이후는 장소별 이전 소속 집합과 현재 서비스별 집합을 비교합니다. 한 서비스만 변경했거나 여러 서비스가 같은 결과로 변경했다면 전파합니다. 서로 다른 변경은 순서를 추측하지 않고 충돌로 남깁니다.

기준 상태는 계정·목록 ID·장소 연결을 고정합니다. 성공 확인 없이 계획 단계에서 기준을 갱신하면 안 됩니다. 빈 소속 집합도 삭제 기록으로 보존합니다.

## 작업 실행 프로토콜 (아직 서비스에 연결하지 않음)

`core/jobs.js`의 `createJob`/`resumeJob`은 아래 검증 흐름을 구현합니다. 어댑터와 원자적 저장 함수를 주입해야 하며 실제 지도용 어댑터는 아직 없습니다. 테스트의 가짜 어댑터는 응답 유실·부분 적용을 재현하기 위한 것이고 실제 서비스 지원의 증거가 아닙니다.

1. 실행 직전 실제 장소 ID·대상 목록 ID·계정·기존 소속을 다시 확인.
2. 작업별 영구 기록: pending → executing → verified / failed / unknown.
3. 쓰기 응답만으로 성공 판단하지 않고 실제 소속을 재조회.
4. 응답 유실 시 동일 저장 버튼을 다시 토글하지 말고 현재 상태 확인.
5. 분류 이동은 추가 작업이 모두 검증된 뒤 제거 실행.
6. 중간 실패 시 다음 일반 스캔 전에 진행 중 작업을 복구. 부분 적용을 사용자 변경으로 오인하지 않도록 작업 당시 목표·계정·목록·장소·이전 상태를 유지.
7. 새 사용자 변경이 작업 중에 발견되면 해당 장소 작업 중단 및 충돌 표시.
8. 서비스별 순차 처리·중단/재개·요청 제한·세션 만료 감지.
9. 전체 쓰기 후 새로운 완전한 스냅샷으로 수렴을 확인한 뒤 checkpoint.

순수 계획기는 작업 도중의 일부 추가 상태를 새로운 사용자 변경과 구별할 수 없으므로 보수적으로 충돌 처리합니다. 실행 중 작업은 저장된 job으로 먼저 복구해야 합니다. 검증된 어댑터와 영구 작업 저장소가 연결되기 전에는 자동 재시도/주기 쓰기를 활성화하면 안 됩니다.
